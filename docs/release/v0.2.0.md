# cookie-net v0.2.0 - Design Lock

**Date:** 2026-10-23
**Compare:** [`v0.1.0...v0.2.0`](https://github.com/jamesgober/cookie-net/compare/v0.1.0...v0.2.0)

**The public API, written down before the code.** v0.2.0 locked every name, signature, behaviour, and error of cookie-net from `0.3.0` to `1.0.0` in [`docs/API.md`](https://github.com/jamesgober/cookie-net/blob/main/docs/API.md), and rewrote the plan from the crate's specification. There is no cookie code in this release; `0.3.0` builds the request side, the response side, and the session helpers against this contract.

## What's in 0.2.0

- **`docs/API.md`.** Every public item with its id, grade (P0 to P3), tier (1 to 3), the version that ships it, its signature, its behaviour with the rfc6265bis section behind it, every error it can return, a cost target, and examples. Five use cases close it: the WASP gateway's credential locator, login with rolling tokens and logout, preferences and flash messages, HTTP/2 cookie crumbs, and an outbound client.
- **A one-call API for the common cases.** `get_unique(header, "__Host-sid")`, `get(header, "theme")`, `SetCookie::new("theme", "dark")`, `session_cookie("__Host-sid", token, 12 * HOUR)`, `SetCookie::delete("__Host-sid")`, `signer.sign(name, value)`, `signer.verify(name, raw, now)`, `sealer.seal(name, text)`, `sealer.open(name, raw, now)`. One error type works with `?` on every call.
- **Rules a cookie cannot break.** Thirteen build-time rules, each with its source: names and values by grammar, the 4096 and 1024 byte limits, `Path` and `Domain` syntax, extension attributes, the 400-day cap, the `__Host-` and `__Secure-` prefixes, and `SameSite=None` and `Partitioned` without `Secure`.
- **Credential reading that fails closed.** `get_unique` and `locate` report duplicates, truncation, and over-long headers instead of guessing, and `locate` counts shadow names (`sid`, `__host-sid`, `__Secure-sid` beside `__Host-sid`) as evidence of cookie tossing.
- **Signed and encrypted cookies for a cluster.** Keyed BLAKE3 with a 128-bit tag and XChaCha20-Poly1305, both through crypt-io; the cookie name inside the MAC and the associated data; optional server-enforced expiry and session binding; key rings with staged rotation and fingerprints, so no node refuses a cookie another node just signed; a 60-second clock-skew allowance.
- **Feature flags** declared ahead of their code: `std` (default), `alloc`, `signed`, `encrypted`, `client`, `jar`. The crate root is now `no_std`.
- **Plan and roadmap.** `dev/PLAN.md` rewritten from the specification, with the enterprise and distributed design, threats T1 to T28 with their tests and costs, performance targets against `cookie`, `biscotti`, and `cookie_store`, defence ideas per version, requests to other crates, and decisions D-004 to D-042. `dev/ROADMAP.md` lists every version to 1.0 with exit criteria.

## Verification

- Local gate on Windows and WSL Ubuntu, Rust stable and 1.85: format, clippy in three feature modes, tests in three modes, documentation with default and all features, and `cargo package` in a fresh target directory.
- Banned-content scan clean.
- CI green on every platform before the tag.

## What's next

`0.3.0` ships the request side (`parse`, `get`, `get_unique`, `locate`, `Cookies` over one header or HTTP/2 crumbs), the response side (`SetCookie` and its builder with every rule), and the session helpers, with unit tests citing each rfc6265bis section, property tests, counting-allocator tests, and four fuzz targets.
