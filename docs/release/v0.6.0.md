# cookie-net v0.6.0 - Optimisation

**Date:** 2026-10-23
**Compare:** [`v0.5.0...v0.6.0`](https://github.com/jamesgober/cookie-net/compare/v0.5.0...v0.6.0)

**Measured, then made faster.** v0.6.0 measured every operation of the plan against `cookie`, `biscotti`, and `cookie_store` on the same bytes, found three that fell short, and fixed two of them without changing a byte of output. Every operation is now at least 20% faster than the best Rust competitor, at equal or stronger security, except sealing and opening encrypted cookies, which are held back by the cipher and have a recorded plan.

## What's in 0.6.0

- **Faster signing and verifying.** Keyed BLAKE3 inputs of up to 512 bytes (every real cookie) are hashed in one call from a stack buffer instead of through seven `update` calls. Signing a 64-byte value went from parity with the `cookie` crate's HMAC-SHA-256 `SignedJar` to 47% faster, verifying to 33% faster. The format vectors are unchanged.
- **Faster reading.** The `Cookie` scanner checks each line as UTF-8 once and slices names and values from it, instead of checking every name and value again. First match, unique lookup, the credential locator, and iteration all became 24 to 33% faster, and are now 43 to 50% faster than the `cookie` crate.
- **A smaller prefixed-duplicate table.** 16 slots instead of 64, so `locate` and `stats` no longer clear 1 KiB per call.
- **`docs/PERFORMANCE.md`.** The ratio table, the machine, the method, criterion results, and the sealing plan. Because the build machine is shared and runs near full load, the 20% rule is decided by a ratio tool that alternates the two sides in short rounds timed with the thread's own CPU time.
- **Benchmarks.** criterion benches of every hot path in `benches/` as the regression baseline, and the public comparison harness [cookie-net-bench](https://github.com/jamesgober/cookie-net-bench) with equivalence tests proving each pair does the same work.

## The one shortfall

Sealing and opening a 64-byte value take about four times as long as the `cookie` crate's AES-256-GCM `PrivateJar`. The time is in crypt-io's XChaCha20-Poly1305, which is slower than hardware AES for small messages. AES-256-GCM with 96-bit random nonces is not equal security for a busy cluster (about 2^32 messages per key), so the plan is XAES-256-GCM through crypt-io as sealed format version `0x03`: 192-bit random nonces at AES speed, the default where the CPU has AES instructions.

## Verification

- Local gate on Windows and WSL Ubuntu, Rust stable and 1.85, every feature mode, and `cargo package` in a fresh target directory.
- The fuzz targets whose code changed (`cookie_header`, `cookie_lines`, `locate`, `signed_verify`, `sealed_open`) ran one hour each on the new code, no findings.
- CI green on every platform before the tag.
