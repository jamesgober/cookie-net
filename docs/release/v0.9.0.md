# cookie-net v0.9.0 - Beta

**Date:** 2026-11-11
**Compare:** [`v0.8.0...v0.9.0`](https://github.com/jamesgober/cookie-net/compare/v0.8.0...v0.9.0)

**Every finding of the adversarial review, fixed test-first.** For the beta, three independent reviews read the crate: one against rfc6265bis-22 and the CHIPS draft, one as an attacker against the threat model, and one for edge cases, arithmetic, and whether the documentation tells the truth. They found 20 defects. None was in signed or sealed cookies, keys, base64url, or the server-side reading and writing of cookies; almost all were in the client jar. 0.8.0 fixed the high one. v0.9.0 fixed the rest, each with a regression test that failed on 0.8.0 before its fix.

## What's in 0.9.0

- **The jar's header survives a bad cookie.** One stored cookie whose name or value was not UTF-8 made `cookie_header` return `None` for the whole request; with a suffix list, a sibling subdomain could use that to strip every cookie from its parent's requests. The `String` form now leaves that cookie out; `write_cookie_header` writes every byte.
- **`import` is untrusted input again in full.** The checksum is not a MAC, so a re-checksummed file could plant a `__Host-` cookie sent over plain HTTP, a supercookie, a duplicate, or a cookie that would never be evicted. `import` now checks every record against the storage rules (an impossible record fails the import), skips domain cookies the importing jar's suffix list refuses, replaces by identity, brings times back to `now`, caps expiries, and applies the jar's limits once. It costs `n log n`: 100,000 records import in about a second, where 0.8 needed time proportional to records times jar size.
- **Every stored cookie exports.** A default path with `;` round-trips; a path over 1024 bytes, or a host that could not be written back, is refused when storing (`IgnoreReason::InvalidRequestUrl`) instead of making the whole export unimportable later.
- **`Jar::store_for`.** Storing now has a request context, as retrieving did: a cross-site response's cookie is ignored unless it is `SameSite=None` or the request was a top-level navigation (rfc6265bis section 5.7 step 18, `IgnoreReason::CrossSite`), and partitioned cookies are kept under the top-level site.
- **The storage rules, exactly.** An IP-address host gets host-only cookies only; `Domain=.` is host-only; expired cookies no longer block a replacement or donate their creation time; cookies of equal path length go by creation time, also after an import; a `__Host-` cookie whose `Path` value fell back to `/` is stored, and one without a `Path` attribute is not (`SetCookieView::has_path`).
- **Reading `Cookie`.** Spaces and tabs around `=` are allowed by the grammar and no longer make a pair skipped. A browser never sends them; reading them keeps a `__Host-sid =x` from hiding beside the real `__Host-sid` (it now counts as a duplicate).
- **Edges.** `Sealer` refuses a cookie over 4096 bytes whatever the name's length, `sealed_len` saturates, and `unknown_attributes` counts attributes, not empty segments.
- **From a further independent review of 0.7.1.** It found one medium and four low issues; three were already among the findings above. The other two are fixed the same way: `session_cookie` and `elevated_cookie` refuse a lowercase `__host-` name, which a browser treats as `__Host-` but the server's own byte-for-byte lookup would never find; and `KeyRing::rotated` no longer promotes a staged key id when the bytes differ, so a node switched to the wrong key is refused at `with_ring` (`DuplicateKeyId`) instead of signing cookies no other node accepts. A ring without a signing key now reports `NoSigningKey`, and the stack buffer used for short MAC inputs is wiped after use.

0.9 adds to the API and changes no signature; `docs/API.md` has the migration note.
