# cookie-net v0.8.0 - Alpha

**Date:** 2026-11-11
**Compare:** [`v0.7.1...v0.8.0`](https://github.com/jamesgober/cookie-net/compare/v0.7.1...v0.8.0)

**A simpler API, checked by its consumers.** v0.8.0 removed the two places where the API offered two ways to do one thing, moved to parse-net 0.9, and rewrote the API reference as a tour whose examples run as tests. web-net and the WASP gates (gatekeeper-io) passed their test suites on it with only the version requirement changed.

## What's in 0.8.0

- **One way to read a header.** `cookie_net::parse(header)` is the way to read every pair; `Cookies::new`, which did the same, is no longer public. `Cookies::with_limits` and `Cookies::from_lines` are unchanged.
- **One `SameSite` type.** The client side used a second enum, `SameSiteAttr`, whose extra variant meant "absent or unknown". `SetCookieView::same_site` and `StoredCookie::same_site` are now `Option<SameSite>`.
- **parse-net 0.9.** The same version web-net uses, so a server stack compiles one parse-net. `Sink` and `Full` are part of cookie-net's API, so this is a breaking change for code that passes its own `Sink`.
- **An API reference that runs.** `docs/API.md` is a task-oriented tour: every public item, what it does, its errors, and examples. Every example in it and in the README is compiled and run as a doctest, which caught one wrong claim and four README examples that had never compiled.

The signed, sealed, and jar export formats did not change: cookies and exports made by 0.7 keep working.

## Fixed

- **A security fix in the client jar.** Three independent reviews ran for the 0.9 beta, and two of them found the same high-severity defect, present since 0.5: when a domain went over its cookie limit, the jar evicted the least recently used cookie whatever its `Secure` flag. A plain-HTTP origin could therefore store 50 cookies for a domain, push a `Secure` session cookie out, and then set its own in its place. Eviction now follows rfc6265bis section 5.7: expired cookies first, then non-secure ones, then secure ones. A regression test runs the attack.
- **`Sealer::open_into`.** The buffer's whole capacity is now wiped before opening and kept on every failure. An early failure used to leave an earlier plaintext in the spare capacity, and an expired cookie dropped the allocation.

## Known issues, fixed in 0.9.0

The same reviews found medium and low defects, all present since 0.4 or 0.5 and none in signed or sealed cookies, keys, or `Cookie` reading. They are listed in `dev/ROADMAP.md`. The most visible: one stored cookie value that is not UTF-8 makes the jar's `cookie_header` return `None`; `Jar::import` adds duplicates and does not re-apply the storage rules to the file; and `Jar::store` takes no request context. web-net and gatekeeper-io use neither the jar nor `open_into`.

## Moving from 0.7

| 0.7 | 0.8 |
|---|---|
| `Cookies::new(header)` | `cookie_net::parse(header)` |
| `SameSiteAttr::Strict`, `Lax`, `None` | `Some(SameSite::Strict)`, `Some(SameSite::Lax)`, `Some(SameSite::None)` |
| `SameSiteAttr::Default` | `None` |
| `parse-net = "0.6"` beside cookie-net | `parse-net = "0.9"` |

web-net and gatekeeper-io use neither removed item and pass no `Sink`, so for them the move is the version requirement alone.

## Verification

- The test suites of web-net 0.9.0 and gatekeeper-io 0.4.1 ran against the 0.8 branch, all features and default features. Both passed. web-net needed no change but the requirement. gatekeeper-io's own cookie code (sign-in, sign-out, the second factor, and CSRF, 18 tests) ran on 0.8; its web-net adapter still pulled web-net's cookie-net 0.7.1 beside it, which works because no cookie-net type crosses between the two, and goes away when web-net moves to 0.8.
- Every fuzz target ran for an hour on the new code, in fork mode with a 60-second timeout: 0.8 million (`cookie_header`) to 81 million (`set_cookie_build`) runs per target, no crash, timeout, or out-of-memory report.
- Performance: the ratio tool ran 0.7.1 and 0.8 alternately under the same load. No row moved beyond the noise between rounds; the parse-net code on cookie-net's hot paths is byte-identical between 0.6.1 and 0.9.3. Every row still meets the 20% rule except sealing, which keeps its recorded plan ([`docs/PERFORMANCE.md`](../PERFORMANCE.md#the-08-recheck)).
- Local gate on Windows and WSL Ubuntu, Rust stable and 1.85, every feature mode, docs for every feature set, and `cargo package` in a fresh target directory.
- CI green on every platform before the tag.

## What's next

`0.9.0` is the beta: an adversarial review with every finding fixed test-first. The pre-1.0 polish pass follows it, before any release candidate.
