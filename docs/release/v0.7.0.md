# cookie-net v0.7.0 - Hardening

**Date:** 2026-10-25
**Compare:** [`v0.6.0...v0.7.0`](https://github.com/jamesgober/cookie-net/compare/v0.6.0...v0.7.0)

**Every threat proven by a test, every parser fuzzed for a day.** v0.7.0 adds no features. It closes the threat table with attack tests, runs every fuzz target for 24 hours, soaks the jar for an hour, makes "no panics in library code" a lint instead of a review rule, and fixes one fail-open case in the system clock.

## What's in 0.7.0

- **The clock fails closed.** `verify_now` and `open_now` used to read a clock set before 1970 as 0, which accepts every value with an expiry and every retired key. Any clock before 2020-01-01, the epoch of the expiry encoding, now reads as the far future, so those are refused and show up as `Expired` and `UnknownKey`. A device without a real-time clock, which reads 1970 plus its uptime, is the realistic case. Values without an expiry, and every function that takes `now` from the caller, are unchanged.
- **No panic paths, enforced.** Clippy denies `unwrap`, `expect`, `panic!`, `todo!`, `unimplemented!`, `unreachable!`, `dbg!`, and print macros in library code, and CI treats warnings as errors. The two remaining debug assertions are gone, so fuzz builds run the same code as release builds.
- **Attack tests T14 to T30** (`tests/threats_crypto_client.rs`): every changed byte of signed and sealed values, values moved to another name, expired and retired values, dropping a compromised key, forged tags with matching prefixes, supercookies in the jar, redaction in every crypto and client type, a flooded jar, secure-cookie shadowing, session binding, extension names, and tampered jar exports. T26, a failing random source, is documented: crypt-io has no hook to make it fail.
- **A jar soak** (`tests/soak.rs`): random `Set-Cookie` streams for 500 hosts with reads, expiry sweeps, and export and import every 20,000 operations, checking that resident memory stays flat.
- **`docs/SECURITY.md`**: the threat model with each defence, its cost, and the test that proves it; what cookie-net does not defend; operating guidance.
- **Docs build for every feature set.** Five intra-doc links pointed at items behind `alloc` or `encrypted`, so `cargo doc` with warnings as errors failed without those features (docs.rs, which builds with every feature, was not affected). CI now builds the docs for ten feature sets.
- **`docs/PLATFORM-NOTES.md`**: what each feature needs from the platform, the platforms CI proves, and how the clock, the random source, constant-time code, and byte order behave.

## Verification

- Fuzzing, at least 24 hours per target on the 0.7.0 code, no findings:

  | Target | Hours | Runs |
  |---|---|---|
  | `cookie_header` | 24.1 | 71.9 million |
  | `cookie_lines` | 24.1 | 341 million |
  | `locate` | 24.0 | 1.74 billion |
  | `set_cookie_build` | 24.0 | 4.42 billion |
  | `signed_verify` | 24.1 | 1.82 billion |
  | `sealed_open` | 24.3 | 655 million |
  | `parse_set_cookie` | 24.0 | 4.02 billion |
  | `cookie_date` | 24.0 | 8.70 billion |
  | `jar_ops` | 24.1 | 104 million |

  The build machine is shared and ran at a load average near 45 on 32 threads throughout. Six times, libFuzzer reported a timeout with an elapsed time of exactly -2 seconds ("timeout after 18446744073709551614 seconds"): the clock stepped backwards, which WSL does when it resynchronises with the host, and libFuzzer reads the negative difference as an unsigned number. Every one of those inputs runs in 3 to 31 ms on its own. Each affected target continued on the same corpus in fork mode, which records timeouts without stopping, until it had 24 hours; the continuation runs had no timeout, crash, or out-of-memory report (`dev/PLAN.md` D-079).
- Jar soak, one hour on WSL Ubuntu: 48,127,000 operations, the jar held at its 3,000-cookie limit, peak resident memory per quarter 19.0, 19.0, 18.1, and 18.4 MiB: no growth.
- Local gate on Windows and WSL Ubuntu, Rust stable and 1.85, every feature mode, and `cargo package` in a fresh target directory.
- CI green on every platform before the tag.
